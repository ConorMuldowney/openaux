# Workspace Custom Prompts & Workflows

Custom prompts and behaviors defined for the OpenAux workspace.

## `/start-ticket` — Autonomous Ticket Workflow

**Trigger**: `/start-ticket <url> [--type <type>] [--title <title>]`

**Purpose**: Execute a complete, end-to-end ticket workflow from issue URL to open PR in a single command.

### Execution Flow

When a user invokes `/start-ticket`, execute these phases sequentially:

#### Phase 1: Terminal Setup (Worktree & Branch Creation)

1. Run the terminal command to parse the issue and create the worktree:
   ```bash
   npm run start-ticket -- <url> [--type <type>] [--title <title>]
   ```

2. Capture the output to extract:
   - Issue number (AUX-###)
   - Issue title
   - Branch type (feat/fix/docs/refactor/test/chore/ci)
   - Worktree path (relative, e.g., `.worktrees/AUX-64/`)
   - Branch name (e.g., `feat/AUX-64-invite-accept-race-conditions`)

3. **Stop if the script fails.** Report the error and do not proceed.

#### Phase 2: Implementation

Invoke the `tackle-ticket-with-docs` skill with these inputs:
- **Issue URL**: The original URL passed by the user
- **Worktree path**: The relative path output from Phase 1

The skill will:
- Read the issue description and acceptance criteria
- Load and follow CONTEXT.md, ADRs, and module boundaries
- Implement the solution with full test coverage
- Stop if tests fail; do not proceed until they pass

#### Phase 3: Commit Organization

Invoke the `chunk-and-commit` skill with:
- **Worktree path**: The same path from Phase 1

The skill will:
- Inspect all unstaged changes in the worktree
- Organize them into logical, semantic commits
- Generate conventional commit messages: `<type>(<scope>): <description>`
- Validate against commitlint rules
- Return the final commit list

#### Phase 4: Push & PR Creation

Invoke the `push-and-create-pr` skill with:
- **Branch name**: From Phase 1 output
- **Base branch**: Always `develop` (not `main`)
- **PR title template**: `AUX-###: <issue title>`

The skill will:
- Push the branch to origin
- Create a pull request
- Validate the PR title matches `.github/workflows/pr-validate-linear.yml`
- Return the PR URL

#### Phase 5: Summary Report

Return a clean, formatted summary containing:
- Issue (AUX-### and title)
- Worktree path
- Branch name
- List of commits created
- PR URL
- Any blockers or assumptions noted during implementation

### Error Handling

- **Phase 1 fails**: Report the terminal error and stop. Do not proceed to Phase 2.
- **Phase 2 fails (tests)**: Report test failures and stop. Do not proceed to Phase 3.
- **Phase 3 fails**: Report commit errors and stop. Do not proceed to Phase 4.
- **Phase 4 fails (PR validation)**: Report PR title/format errors. Suggest corrections.

### Decision Rules

1. **Missing issue metadata**: If the issue cannot be fetched and `--title` is not provided, ask the user before proceeding.
2. **Branch name violations**: If the generated branch name fails validation, stop and explain the violation.
3. **Docs conflicts**: Prefer ADRs (`docs/adr/`) over general documentation when guidance conflicts.
4. **Scope creep**: If implementation requires broader changes, keep the ticket minimal and document follow-ups separately.

### Notes for Agent Orchestration

- The worktree is created **outside the main working directory** at `.worktrees/AUX-<number>/`. This is intentional for isolation.
- Phase 2 (implementation) must occur **inside the worktree directory** to ensure changes are scoped to the feature branch.
- All terminal operations should use `run_in_terminal` with `mode=sync` for short operations and `mode=async` for longer ones.
- Skill invocations should use `runSubagent()` to delegate to `tackle-ticket-with-docs`, `chunk-and-commit`, and `push-and-create-pr`.

### Environment Variables

The workflow uses these optional environment variables (configured in `.env.local`):

- `LINEAR_API_KEY`: For fetching Linear issue metadata (optional; falls back to manual input)
- `GITHUB_TOKEN`: For GitHub issue access (optional; works without for public repos)
- `WORKTREE_BASE_PATH`: Base directory for worktrees (defaults to `.worktrees/`)

## Repository Standards

### Commit Message Format

All commits must follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>
```

**Valid types**: feat, fix, docs, refactor, test, chore, ci  
**Scope**: The module or feature being changed (e.g., `invites`, `scoring`, `lifecycle`)  
**Description**: Present tense, lowercase, no period

**Examples**:
- `feat(invites): add race condition detection`
- `test(invites): add integration tests for simultaneous accepts`
- `fix(lifecycle): resolve state transition race`

Commits are validated by Husky + commitlint before they're pushed.

### Branch Naming

All branches follow the pattern: `<type>/AUX-<number>-<slug>`

**Examples**:
- `feat/AUX-64-invite-accept-race-conditions`
- `fix/AUX-123-state-transition-race`
- `docs/AUX-42-lifecycle-documentation`

Validation occurs in `scripts/create-worktree.mjs`.

### PR Format

Pull request titles must follow: `AUX-###: <title>`

**Valid**:
- `AUX-64: Add integration tests for invite-accept API`
- `AUX-123: Fix state transition race condition`

**Invalid**:
- ❌ `Add integration tests` (missing AUX reference)
- ❌ `AUX-64 Add tests` (missing colon and space)

Enforced by `.github/workflows/pr-validate-linear.yml`.
